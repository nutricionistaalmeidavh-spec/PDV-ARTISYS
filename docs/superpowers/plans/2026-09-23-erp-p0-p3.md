# ERP P0-P3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implementar no PDV ArtiSys a base gerencial P0, gestão empresarial P1, bancos/conciliação P2 e automação financeira P3, preservando os serviços canônicos existentes e exigindo E2E Electron real para cada capacidade.

**Architecture:** O `finance-service.js`, vendas, compras, caixa, EventBus/outbox, auditoria, backup e importador atuais continuam autoritativos. As novas capacidades entram como serviços focados em dimensões gerenciais, reporting, extratos/conciliação e recorrências/alertas; mutações são idempotentes e as projeções nunca criam um segundo livro financeiro. A UI desktop usa os mesmos padrões de `operational-pages.js`/`api-client.js` e as rotas novas ficam isoladas em `server/erp-finance-router.js`.

**Tech Stack:** Node.js >=22, CommonJS no PDV, SQLite, Electron 39, Playwright 1.63, Node test runner, `@artisys/finance-domain` 0.1.0 vendorizado/pinado.

**Spec:** `docs/superpowers/specs/2026-09-23-erp-p0-p3-design.md`

## Global Constraints

- Não duplicar EventBus, outbox, auditoria, RBAC, backup/restore, sistema de módulos ou importador CSV/XLSX existentes.
- Não substituir `js/domains/finance/finance-service.js`; estender contratos sem quebrar chamadas existentes.
- Reusar lógica madura de `sistemafinanceiro`, adaptada ao modelo do PDV.
- Reusar `@artisys/finance-domain` para fingerprints, regras e sugestões de conciliação.
- Toda mutação sujeita a retry deve possuir chave/idempotência persistida.
- Importar extrato nunca baixa conta automaticamente; baixa/vínculo só após confirmação explícita.
- Core local-first, sem serviço pago obrigatório.
- Migrations somente incrementais e preservando instalações existentes.
- Todo recurso novo precisa de teste unitário/integração, E2E Electron real, registro no `qa/artisys-qa.config.json`, inclusão em `full` e `release.criticalFlows`.
- `npm run verify` e `npm run verify:release` precisam ficar verdes ao final de cada fase.

## Review Focus

1. **OFX duplicado versus pagamentos legítimos repetidos:** a mesma linha do mesmo arquivo não pode duplicar, mas dois PIX idênticos em linhas/FITIDs diferentes devem coexistir. Coberto em Task 8.
2. **Datas no fim do mês/competência e fuso:** vencimento 29/30/31 e competência devem ser tratados por data de negócio, sem deslocar um dia por timezone. Coberto em Tasks 4 e 11.
3. **Restart durante geração de recorrência:** reabrir o app e gerar novamente não pode criar segunda ocorrência. Coberto em Task 11 e E2E da Task 13.
4. **Baixa parcial + estorno:** DRE/caixa realizado deve refletir somente liquidações ativas e voltar corretamente após estorno. Coberto em Tasks 4 e 6.
5. **Projeção negativa/alertas:** alertas e projeções são derivados; marcar/ocultar alerta não pode alterar saldo, conta ou lançamento. Coberto em Task 12.
